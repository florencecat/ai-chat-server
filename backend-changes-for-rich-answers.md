# Правки бэкенда `ai-chat-server`

Клиентский рендер размеченных ответов уже в приложении. Здесь — что нужно
поменять на сервере: чтобы разметка была предсказуемой, чтобы предложенные
события и записи доходили до карточек, и чтобы стали возможны `urgency` и
красные флаги из плана.

Опорные документы: [`server-readme.md`](server-readme.md) — действующий контракт,
[`ai-advice-feature-plan.md`](ai-advice-feature-plan.md) — целевая фича.

Правки отсортированы по убыванию отдачи. У каждой — что сейчас, почему это
проблема, что сделать, и как проверить.

---

## Что сервер получает и отдаёт сегодня

Фиксирую фактическое состояние, потому что несколько правок ниже — именно про
расхождение факта с README.

**Запрос** (`AIChatController.sendMessage`, `lib/services/ai_service.dart:661`):

```jsonc
{
  // ВЕСЬ диалог, упакованный в строку: jsonEncode([{role, content}, …])
  "message": "[{\"role\":\"system\",\"content\":\"Ты ветеринарный ассистент…\"},…]",
  // дублирует данные, уже вложенные в system-сообщение выше
  "attachment": { /* … */ }
}
```

В `message` лежат: системная инструкция, контекст питомца (`PetContextBuilder.build`
— имя, вид, порода, возраст, пол, вес, аллергии, хронические болезни, обработки,
прививки, активные препараты, тревожные симптомы из заметок) и последние
10 сообщений диалога.

**Ответ**, который клиент умеет разобрать:

```jsonc
{
  "response": {
    "response": "текст ответа",     // или answer / text / message
    "events":  [ /* … */ ],
    "entries": [ /* … */ ]
  },
  "cached": false,
  "tier": "premium",
  "quota": { "requests_today": 3, "limit_day": 200, "limit_minute": 5 }
}
```

`response` может быть и просто строкой — тогда карточек не будет, но текст
покажется.

---

## 1. `SYSTEM_PROMPT`: зафиксировать подмножество разметки

**Сейчас.** Формат ответа промптом не задан, и модель размечает текст как
придётся.

**Почему это проблема.** Клиент рендерит не весь Markdown, а ровно подмножество
из `lib/models/chat_markup.dart`. Всё, что вне подмножества, выводится сырым
текстом: таблица становится частоколом `|`, ссылка — `[текст](url)`.

**Что сделать.** Добавить в `SYSTEM_PROMPT` блок о формате:

```text
Формат ответа. Используй только эту разметку:
  **жирный** — для терминов, доз, названий препаратов;
  *курсив* — редко, для смысловых оговорок;
  `моноширинный` — для дозировок и числовых значений;
  ## и ### — заголовки разделов (## — не чаще одного на ответ);
  «- » — маркированный список, «1. » — нумерованный (порядок действий);
  --- — разделитель перед итогом или предупреждением.

Запрещено: таблицы, конструкции вида _подчёркивание_, тройные обратные
апострофы, ссылки [текст](url), HTML, эмодзи-заголовки.
Списки — не глубже двух уровней вложенности.
Абзацы разделяй пустой строкой.
```

Про `_подчёркивание_` отдельно: на клиенте оно отключено намеренно — модель
цитирует в ответах ключи вида `day_requests`, и разметка по `_` рвала бы их
пополам. Если промпт начнёт выделять подчёркиванием, пользователь увидит сами
символы.

**Проверка.** Прогнать десяток типовых вопросов и убедиться, что в ответах нет
`|`, `[`, ``` ``` ``` и `_` в роли выделения.

## 2. Строгая схема ответа вместо «произвольного JSON»

**Сейчас.** README описывает `response` как «произвольный JSON от модели».
Клиент искал текст только по ключу `response` и иначе отдавал `toString()` — в
пузырь попадал Dart-дамп карты вида `{events: [...], urgency: monitor}`.

**Что уже починено на клиенте.** `ChatResult.answerText()`
([`ai_api_dto.dart:63`](../lib/models/ai_api_dto.dart:63)) перебирает
`response` / `answer` / `text` / `message`, а карта без текстового поля даёт
ошибку с кнопкой повтора вместо мусора в пузыре. Это страховка, а не контракт.

**Что сделать на сервере.** Объявить схему и провалидировать ответ модели
**до** отдачи клиенту и **до** записи в кеш. Невалидный JSON — это `LLM_ERROR`
(и, по-хорошему, один повтор запроса к модели), а не «ответ».

```jsonc
{
  "type": "object",
  "required": ["response"],
  "additionalProperties": false,
  "properties": {
    "response": { "type": "string", "minLength": 1 },
    "events":   { "type": "array", "maxItems": 3, "items": { "$ref": "#/$defs/event" } },
    "entries":  { "type": "array", "maxItems": 5, "items": { "$ref": "#/$defs/entry" } }
  }
}
```

Механика различается по провайдерам, и это ровно то, для чего в сервисе есть
абстракция `llm`:

- **YandexGPT** — `response_format.json_schema` (нативная поддержка схемы);
- **GigaChat** — function calling: объявить функцию `answer` с этой схемой
  параметров и заставить модель вызвать её.

`maxItems` не косметика: три карточки под ответом — уже полэкрана, и на пятой
пользователь перестаёт их читать.

## 3. Схема `events`: сегодня работают три категории из восьми

**Сейчас.** Клиент разбирает элемент `events` так
([`suggested_event.dart:46`](../lib/models/suggested_event.dart:46)):

| Поле       | Тип    | Что делает клиент                                            |
|------------|--------|--------------------------------------------------------------|
| `name`     | string | Пусто или нет поля → «Напоминание»                            |
| `category` | string | `EventCategories.fromAiId` — см. ниже                          |
| `datetime` | string | ISO-8601, **местное время пользователя** (см. правку 5)        |
| `repeat`   | string | `none` / `daily` / `weekly` / `monthly`; иначе → `none`         |

**Проблема.** `fromAiId` ([`event.dart:282`](../lib/models/event.dart:282))
знает ровно три значения: `health`, `grooming`, `other`. Категории «Питание»,
«Прогулка», «Дрессировка», «Вакцинация» в приложении есть и у них есть id, но
через ИИ в них не попасть — всё лишнее молча схлопывается в «Другое».

**Что сделать.** Развилка:

- **минимум** — перечислить в схеме `"category": {"enum": ["health","grooming","other"]}`
  и не давать модели выдумывать остальные: сейчас она может прислать `food`, и
  событие просто потеряет категорию;
- **правильно** — расширить маппинг на клиенте до всех восьми категорий, а в
  схеме перечислить полный список. Это правка на клиенте, я её сделаю по
  вашему слову; серверная схема должна поменяться синхронно.

Повторы `repeat` ограничить теми четырьмя, что клиент понимает: `yearly`,
который модель охотно предлагает для прививок, превратится в разовое событие.

## 4. Схема `entries`: контракт уже описан в клиенте

Клиент отбрасывает предложение целиком, если трекер незнакомый **или** не
хватает ключевого значения (`SuggestedEntry.fromAi`, поле `isComplete`) — по
такой карточке всё равно ничего не записать. Поэтому схему в промпте надо задать
точно, иначе часть предложений тихо исчезает.

| `tracker` | Обязательное поле | Остальные поля                                                                |
|-----------|-------------------|--------------------------------------------------------------------------------|
| `mood`    | `mood`            | `mood`: `happy` / `calm` / `sick` / `playful`                                   |
| `weight`  | `weight_kg` > 0   | число в килограммах                                                             |
| `symptom` | `symptom`         | `severity`: `mild` / `moderate` / `severe` (по умолчанию `mild`), `note`         |
| `walk`    | `minutes` > 0     | `activities`: `active` / `calm` / `dogGames` / `training`                        |
| `meal`    | `grams` > 0 **или** `food` | `appetite` 1–5, `kind`: `natural` / `dry` / `wet` / `treat`            |
| `note`    | `text`            | —                                                                                |

Допустимые `symptom` ([`suggested_entry.dart:332`](../lib/models/suggested_entry.dart:332)):
`vomiting`, `diarrhea`, `refused_food`, `lethargy`, `sneezing`, `coughing`,
`scratching`, `limping`.

У каждого элемента есть `datetime` — те же правила, что у событий.

## 5. Часовой пояс: сейчас его в запросе нет вообще

**Это самая скрытая из правок, и я бы делал её первой после промпта.**

**Сейчас.** В запрос не уходит ни текущее время пользователя, ни смещение пояса.
Модель всё равно вынуждена проставить `datetime` — и проставляет стенные часы
пользователя, помечая их суффиксом `Z`, будто это UTC. Это зафиксировано на
реальном ответе: на «напомни сегодня погулять в 10:00» пришло
`2026-07-19T10:00:00Z`.

Клиенту пришлось подстроиться: `parseAiDateTime`
([`ai_datetime.dart`](../lib/models/ai_datetime.dart)) **отбрасывает**
обозначение пояса, потому что разбор как настоящего UTC уносил событие на
смещение (для Москвы — на три часа вперёд).

**Чем плохо.** Модель не знает не только пояса, но и текущей даты. «Напомни
через неделю» и «запиши на завтра» она считает от даты, которую предполагает
сама, — и промахивается тем сильнее, чем дальше обучающий срез от сегодня.

**Что сделать.**

1. Клиент присылает своё время и смещение — правка маленькая, я её сделаю:
   ```jsonc
   { "messages": [ /* … */ ], "client_time": "2026-09-11T14:32:00+03:00", "tz": "Europe/Moscow" }
   ```
2. Сервер подставляет их в системную инструкцию:
   ```text
   Сейчас у пользователя: 2026-09-11, четверг, 14:32 (Europe/Moscow).
   В поле datetime пиши МЕСТНОЕ время пользователя в формате
   YYYY-MM-DDTHH:MM:SS, без «Z» и без смещения.
   ```
3. Если `client_time` не пришёл (старая сборка) — поведение прежнее.

**Совместимость.** Установленные сборки не сломаются: клиент отбрасывает суффикс
пояса, поэтому и `10:00:00` без суффикса, и `10:00:00Z`, и `10:00:00+03:00`
(если смещение — пользовательское) дают одинаковые 10:00 местного времени.
Единственный вариант, который сломается, — настоящий UTC, и его как раз не
должно быть.

## 6. Принимать историю массивом; кеш почти наверняка не работает

**Сейчас.** Клиент кладёт весь диалог строкой в поле `message`.

**Два следствия.**

1. **Кеш.** README обещает, что «повторные одинаковые запросы не тратят квоту».
   Ключ, как бы он ни считался, выводится из тела запроса — а в тело входят
   последние 10 сообщений и контекст питомца. Побайтово одинаковых запросов при
   этом практически не бывает: достаточно одного нового сообщения в треде или
   изменившегося веса в профиле. Экономии квоты, скорее всего, нет вовсе.
   *Это вывод по README — исходников сервера в этом репозитории нет, проверьте
   по пакету `cache`.*
2. **`MAX_MESSAGE_LEN` (4000)** режет не вопрос пользователя, а вопрос вместе с
   историей и контекстом питомца. Длинный тред обрежется с конца — то есть
   ровно на самом свежем сообщении, том единственном, на которое надо ответить.

**Что сделать.**

- Принимать `{"messages": [{"role","content"}, …]}` рядом со старым `message`
  (старое поле оставить, пока живы установленные сборки).
- Ключ кеша считать по: последнее сообщение пользователя + `pet_id` +
  `prompt_version` + модель. Не по всему телу.
- Лимит длины применять к последнему пользовательскому сообщению, а историю
  ограничивать числом сообщений и суммой токенов отдельно.
- Системную инструкцию и контекст питомца собирать на сервере, а не принимать
  от клиента: сейчас клиент присылает свою системную строку («Ты ветеринарный
  ассистент…»), и она перекрывает серверный `SYSTEM_PROMPT`. Пока это так,
  правка 1 наполовину бессмысленна — формат ответа задаётся из APK и меняется
  только с релизом. Контекст питомца пусть приходит отдельным полем
  (`pet_context`), а склейка — серверная.

Последний пункт по важности не уступает первому: он решает, можно ли вообще
менять поведение ассистента без релиза приложения.

---

## 7. `prompt_version` в ответе и в ключе кеша

Добавить `prompt_version` в тело `/chat` и включить её в ключ кеша.

Без этого: после правки промпта пользователи ещё `CACHE_TTL` (по умолчанию час)
получают ответы по старой версии, и сравнить v2 с v1 — задача Фазы 5 плана — не
на чем. Клиент неизвестные поля в теле игнорирует, так что поле можно добавлять
хоть сегодня.

## 8. Поля Фазы 4: `urgency`, `red_flags`, `follow_up_questions`

**Клиент к этим полям уже готов и ждёт их.** Чип срочности, баннер тревожных
признаков с кнопкой «Ближайшая клиника» и тапабельные уточняющие вопросы
реализованы и лежат в сборке «спящими»: пока сервер полей не отдаёт, ни один из
виджетов не строится. Сделано так намеренно — иначе серверная правка потребовала
бы ещё и релиза приложения с прохождением модерации RuStore.

Разбор терпимый: незнакомый уровень `urgency` трактуется как `monitor`,
отсутствие поля — как «метаданных нет» (это разные вещи), не-строки в списках
отбрасываются, списки обрезаются до 5 признаков и 3 вопросов. Поэтому поля можно
выкатывать **по одному** и в любом порядке, не согласовывая с релизным циклом
приложения.

Чтобы включить:

1. Расширить схему из правки 2:
   ```jsonc
   "urgency": { "enum": ["self_care", "monitor", "vet_24h", "emergency"] },
   "red_flags": { "type": "array", "items": { "type": "string" } },
   "follow_up_questions": { "type": "array", "maxItems": 3, "items": { "type": "string" } }
   ```
2. Добавить серверную валидацию: если в тексте ответа есть маркер из
   `red-flags.yaml`, а `urgency` ниже `vet_24h` — **поднять** уровень и
   залогировать расхождение. Понижать автоматически нельзя ни при каких
   условиях: цена ошибки несимметрична.
3. Неизвестное значение `urgency` приводить к `monitor`, а не отдавать ошибку.
4. `urgency` не кешировать отдельно от текста — они должны меняться вместе.

5. Добавить в PocketBase, в коллекцию `chats`, текстовую колонку
   `advice_json` — клиент уже отправляет её в `pushChat` рядом с `events_json`
   и `entries_json`. Без колонки метаданные просто не переживут восстановление
   истории на новом устройстве (ровно та же ситуация, что сейчас у
   `entries_json`, — см. комментарий в `restoreThreadsFromCloud`).

## 9. Мелочи, которые дёшево поправить заодно

- **`max_tokens`.** Ограничить длину ответа. Пузырь на 2000 токенов никто не
  дочитывает, а квота и деньги тратятся полностью. Разумный потолок — 500–700
  токенов, с явной инструкцией в промпте уложиться в 5–7 абзацев.
- **Поле `attachment`.** Клиент шлёт его в теле запроса и **одновременно**
  вкладывает те же данные в system-сообщение. Либо сервер начинает его
  использовать (и тогда клиент перестаёт дублировать), либо поле надо убрать из
  контракта — сейчас оно молча игнорируется.
- **`GIGACHAT_SKIP_TLS=true` по умолчанию.** Для сертификатов Сбера правильнее
  положить в образ корневой сертификат НУЦ Минцифры, чем выключать проверку.
  Настройка называется по-гигачатовски, но выключает проверку для всего
  HTTP-клиента — включая Yandex-провайдера, PocketBase и RuStore.
- **Логирование.** К уже описанным в README полям добавить: `prompt_version`,
  длину ответа в символах, число элементов в `events` / `entries`, факт
  срабатывания валидации красных флагов, факт повтора запроса после невалидного
  JSON. Это входные данные для Фазы 5 плана.

## Порядок, в котором я бы это делал

1. **Правка 6, последний пункт** — перенести системную инструкцию на сервер.
   Пока формат ответа задаётся из APK, всё остальное меняется только с релизом.
2. **Правка 1** — формат разметки в промпте. Сразу виден результат в приложении.
3. **Правка 5** — часовой пояс. Чинит реально неверные даты в напоминаниях.
4. **Правки 2–4** — строгая схема ответа, событий и записей.
5. **Правки 6 (кеш) и 7** — квота и возможность сравнивать версии промпта.
6. **Правка 8** — `urgency` и красные флаги. Клиентская часть готова, так что
   это чисто серверная работа: как только поля появятся в ответе, они начнут
   отображаться в уже установленных сборках.

## Чего на сервере делать НЕ нужно

**Стриминг.** В плане он есть, в текущей архитектуре его нет, и ради оформления
ответов он не требуется. «Печать» — клиентская анимация
(`AIChatController.fakeStream`), и разбор разметки к ней приспособлен:
незакрытые `**` и `` ` `` трактуются как открытые, поэтому маркеры не мелькают
текстом ни на одном кадре (это покрыто тестом, который проходит по всем кадрам
посимвольно). Если SSE появится позже, рендер менять не придётся — поменяется
только источник чанков.
